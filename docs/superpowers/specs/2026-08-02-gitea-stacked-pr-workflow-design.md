# Gitea 堆叠 PR 工作流设计

**日期：** 2026-08-02

**状态：** 已由用户逐节批准，待书面规格复核

**基线版本：** `13c187fe4b98883219e2e74db3da188a393dcb21`

**代码托管：** `https://git.doorai.cn/shuo/youzheng-huicui`

## 1. 背景与问题

多个 Codex 任务存在前后依赖时，目前依靠人工创建和维护 Git 分支及 PR，容易出现：

1. 父子 PR 的合并顺序混乱。
2. 上层 PR 错误地以 `main` 为目标，因而在页面中重复展示下层全部改动。
3. 调整任务依赖后，分支历史、PR 目标分支和 PR 描述不能同步更新。
4. 多个 Codex 会话同时操作同一个堆栈，可能覆盖彼此的远程提交。
5. 合并动作缺少明确的计划、审批边界和故障恢复规则。

上层分支在 Git 历史中包含下层提交是堆叠分支的正常结构。需要解决的是 PR 的目标分支和可见差异：每个 PR 必须指向直接父分支，只显示本层改动。

## 2. 目标

建立一套由 Git Town 管理、Gitea 承载、Codex 执行的堆叠 PR 工作流，支持：

1. 创建堆叠分支。
2. 创建父子 PR。
3. 重排分支依赖。
4. 同步更新 PR 目标分支和堆栈导航。
5. 在明确批准后按依赖顺序合并。
6. 在并发更新、冲突、网络中断或部分失败时安全停止并恢复。

完成后，新的 Codex 任务只依据仓库内配置和文档，即可正确维护堆叠 PR；没有用户对准确合并计划的明确批准时，不得合并到 `main`。

## 3. 非目标

- 本阶段不配置 Gitea Actions、自建 Runner 或其他 CI。
- 不迁移或重写历史遗留分支和已关闭 PR。
- 不开发自有的完整堆叠 PR 管理器或重复实现 Git Town。
- 不支持跨 fork 的堆叠 PR；Gitea 子 PR 自动重定向仅按同仓库分支设计。
- 不允许自动解决包含业务语义判断的冲突。
- 不把 Gitea Token 或其他凭据提交到仓库。

## 4. 方案选择

采用 **Git Town + Gitea 原生 PR**：

- Git Town 负责分支层级、同步、重排、PR 创建/更新和合并编排。
- Gitea 是代码、PR 目标关系和评审状态的权威来源。
- Gitea 的 `RETARGET_CHILDREN_ON_MERGE` 能力负责父 PR 合并后的直接子 PR 重定向；实施时先读取并验证实际配置。
- Codex 执行操作、展示依赖图和合并计划，并实施审批门禁。

未选择的方案：

- 自建脚本调用 Gitea REST API：控制细，但需要自行维护重排、冲突、回滚和 API 兼容，维护成本过高。
- 纯手工维护父子 PR：部署简单，但无法可靠解决多任务并发和重排错误。

## 5. 总体架构与职责

### 5.1 Gitea

- 仓库：`shuo/youzheng-huicui`。
- `main` 是最终集成分支。
- PR 创建后，其目标分支关系是堆栈父子结构的权威状态。
- 负责评审、权限、分支保护、合并和子 PR 重定向。

### 5.2 Git Town

- 使用仓库级 `git-town.toml` 共享非敏感配置。
- `[branches].main` 配置为 `main`。
- `[hosting].dev-remote` 配置为 `gitea`；分支推送和 PR 操作不使用当前 GitHub `origin`。
- 托管类型设为或自动识别为 Gitea。
- PR 提案启用堆栈 breadcrumb，便于从任意 PR 查看父子关系。
- Gitea Token 通过运行时环境变量或本机安全配置提供，绝不写入 `git-town.toml`。

实施时固定并记录已验证的 Git Town 版本，避免不同版本的配置和命令语义漂移。

### 5.3 Codex

- 创建分支、提交、推送、创建 PR、重排和同步堆栈。
- 操作前后展示堆栈图、PR 目标分支和提交 ID。
- 在独立 Git worktree 中执行各任务，避免共用工作区。
- 每个堆栈指定一个主协调会话；只有主协调会话可以调整父子关系、更新整组 PR 或执行合并。子任务会话只修改并提交自己负责的分支，然后把结果交回主协调会话。
- 发现语义冲突、远程并发更新或权限异常时停止。
- 合并 `main` 前生成精确计划并等待明确批准。

## 6. 分支和 PR 模型

新堆栈使用稳定、可读且可排序的命名：

```text
stack/<topic>/01-<task>
stack/<topic>/02-<task>
stack/<topic>/03-<task>
```

示例：

```text
main
└── stack/member-fix/01-api
    └── stack/member-fix/02-ui
        └── stack/member-fix/03-e2e

PR 1: 01-api -> main
PR 2: 02-ui  -> 01-api
PR 3: 03-e2e -> 02-ui
```

序号表达当前计划顺序，但父子关系仍以 PR 目标分支为准。重排时可同步重命名序号；若重命名会增加风险，则保留分支名并以更新后的 PR 目标及 breadcrumb 表达真实顺序。

## 7. 创建堆栈流程

1. 拉取 `gitea/main`，检查工作区干净并记录起始 SHA。
2. 第一个任务从 `main` 创建；后续任务从直接父分支创建。
3. 每一层只包含该任务需要的新增提交。
4. 每完成一层，运行该层相关的本地测试后再提交和推送。
5. 使用 Git Town 为整组分支创建或更新 PR。
6. 检查每个 PR 的源分支、目标分支、提交范围和可见差异。
7. 在 PR 描述中维护 breadcrumb，标明当前层、父层和子层。
8. 向用户报告堆栈图、PR 链接和未通过的检查。

PR 可在开发期间保持草稿状态；进入合并计划前必须退出草稿。

## 8. 重排依赖流程

重排开始前必须展示当前图和目标图。例如：

```text
调整前: main <- 01-api <- 02-ui <- 03-e2e
调整后: main <- 01-api <- 03-e2e <- 02-ui
```

执行规则：

1. 获取全部相关远程分支和 PR 的最新状态。
2. 确认没有其他会话更新相关远程 SHA。
3. 使用 Git Town 的父级调整、交换和堆栈同步能力重排本地历史。
4. 只使用带租约的安全更新；禁止无租约强制推送。
5. 更新全部受影响 PR 的目标分支和 breadcrumb。
6. 验证提交未丢失、未重复，且每个 PR 只显示本层差异。
7. 展示重排后的最终图和提交 ID。

如果发生语义冲突、远程租约失败或 API 部分失败，停止后续写操作并进入异常恢复流程。

## 9. 合并流程与审批门禁

### 9.1 合并前检查

Codex 必须：

1. 获取最新远程状态，确认 `main` 和堆栈未发生未处理的变化。
2. 确认 PR 不是草稿，并满足 Gitea 已配置的评审要求。
3. 运行每层要求的本地测试并报告结果；不得把“没有 CI”描述为“测试通过”。
4. 确认各 PR 的目标分支和差异正确。
5. 输出按底层到上层排列的 PR、分支、源 SHA、目标分支和合并策略。
6. 明确等待用户批准，不得把此前对设计或一般流程的批准当作本次合并授权。

一次批准只对展示出的 PR、SHA、目标分支和顺序有效。任一项变化都会使批准失效。

### 9.2 合并执行

批准后按底层到上层执行：

```text
01-api -> main
02-ui  -> main
03-e2e -> main
```

每完成一层：

1. 查询 Gitea，确认合并结果和 `main` 新 SHA。
2. 确认直接子 PR 已被重定向到 `main`。
3. 确认子 PR 差异未重新包含已合并层。
4. 确认子 PR 的源 SHA 仍与批准计划一致。
5. 全部满足后才执行下一层。

堆叠 PR 默认使用 **fast-forward**。如仓库规则不允许，则只可采用保留原提交身份的普通 merge。禁止 squash 和会重写提交身份的 rebase merge，因为它们可能使子 PR 再次显示已合并层。

## 10. 并发控制

- 同一堆栈同一时间只能有一个主协调会话执行重排、整组 PR 更新或合并；子任务会话不得执行这些结构性操作。
- 不同任务使用独立 worktree 和独立分支。
- 每次结构性操作开始时记录整组分支的预期 SHA 和 PR 目标；每次写远程或调用 PR API 前重新比较实际状态。
- 历史调整只使用 `force-with-lease`；租约失败即停止。
- PR 创建后，Codex重新从 Gitea PR 目标关系推断父级，避免依赖陈旧本地状态。
- 不同堆栈可并行工作，但都不得绕过 `main` 合并门禁。

## 11. 权限与凭据

### 11.1 `main` 分支保护

计划为 `main` 配置：

- 禁止直接推送。
- 禁止强制推送和删除。
- 只能通过 PR 合并。
- 保留现有评审要求；如需新增或改变评审门槛，另行批准。

这是 Gitea 服务端写操作。实施时先读取当前配置，展示差异和回退办法，并再次取得用户批准后才修改。

### 11.2 Gitea Token

- Token 至少具备 Git Town 官方要求的仓库读写权限，并由专用或明确授权的账号持有。
- 优先通过 `GIT_TOWN_GITEA_TOKEN` 运行时环境变量或操作系统凭据存储注入。
- 禁止写入仓库文件、shell 历史、测试报告、PR、日志或对话输出。
- 使用 `git town config --redact` 等脱敏方式检查有效配置。

## 12. 异常恢复

### 12.1 重排冲突

- 停止操作，不自动选择业务代码。
- 使用 Git Town 的撤销能力或 Git 的安全中止流程恢复到开始前状态。
- 记录冲突分支和文件，等待用户或负责该任务的 Codex 会话处理。

### 12.2 远程并发更新

- `force-with-lease` 或 SHA 检查失败后不得重试覆盖。
- 重新读取远程堆栈，展示预期与实际差异，再决定重新同步或重新规划。

### 12.3 PR API 部分失败

- 重新扫描整组 PR。
- 列出已成功、未执行和状态不一致的项目。
- 更新操作必须幂等；只有恢复一致状态后才能继续。

### 12.4 合并中断

- 网络中断时先查询 Gitea 的真实状态，不依据本地命令返回值猜测。
- 已进入 `main` 的提交不回退、不强制重写。
- 如需撤销已合并变更，创建独立 revert PR。
- 如果剩余 PR 的 SHA、目标分支或顺序与批准计划不同，重新请求批准。

## 13. 验证策略

验收使用临时基线和临时堆栈，不修改 `main`：

```text
validation-base
└── validation-01
    └── validation-02
        └── validation-03
```

### 13.1 配置验证

1. `git-town.toml` 可被固定版本的 Git Town 正确读取。
2. 主分支为 `main`，开发远程为 `gitea`，托管平台识别为 Gitea。
3. `git town config --redact` 不输出 Token。
4. 仓库及 Git diff 中不存在凭据。

### 13.2 创建与差异验证

1. 创建三层临时分支及三个父子 PR。
2. 验证各 PR 的目标分支正确。
3. 每层使用独立标记改动，确认 PR 只显示本层差异。
4. 验证 breadcrumb 能从任一 PR 导航整个堆栈。

### 13.3 重排与并发验证

1. 把第三层调整到第二层之前。
2. 验证目标分支、breadcrumb、提交范围和差异同步更新。
3. 验证没有提交丢失、重复或意外进入其他层。
4. 模拟远程 SHA 变化，确认带租约推送拒绝覆盖。
5. 模拟冲突，确认流程停止并可恢复到操作前状态。

### 13.4 合并与重定向验证

1. 只在临时基线上合并第一层。
2. 验证 Gitea 自动把直接子 PR 重定向到临时基线。
3. 验证子 PR 差异未包含已合并层。
4. 完成临时堆栈的自下而上合并，验证每一步状态检查。
5. 列出临时 PR 和分支，获得清理批准后再删除。

## 14. 计划新增或修改的内容

- `git-town.toml`：团队共享的非敏感 Git Town 配置。
- 项目级 Codex/代理说明：记录堆叠 PR 操作规则和 `main` 合并审批门禁；实施时先检查并兼容现有 `AGENTS.md` 或等效说明。
- `docs/workflows/stacked-pr.md`：创建、重排、同步、合并和故障恢复手册。
- 必要的验证脚本或命令清单：只补充轻量、可重复的安全检查，不实现新的堆叠 PR 管理器。

服务端可能修改：

- 验证并在必要时启用 Gitea `RETARGET_CHILDREN_ON_MERGE`。
- 为 `main` 配置分支保护。

所有服务端修改必须在实施阶段读取现状、展示差异并再次获批。

## 15. 验收标准

1. 新 Codex 任务能从 `main` 创建三层堆叠分支和正确的父子 PR。
2. 每个 PR 只显示本层改动。
3. 重排后分支历史、PR 目标和 breadcrumb 一致，提交不丢失。
4. 远程并发更新不会被覆盖，语义冲突不会被自动处理。
5. 临时堆栈验证 Gitea 子 PR 自动重定向和自下而上合并流程。
6. 没有准确、仍有效的用户批准时，Codex 不会合并到 `main`。
7. 仓库、Git 配置展示、日志和 PR 中不包含 Gitea Token。
8. 工作流文档包含创建、重排、恢复和合并示例。
9. 本阶段不引入或启用 CI。
