# UAT 全角色业务旅程自动扫描设计

**日期：** 2026-07-29
**状态：** 已由用户逐节确认
**基线版本：** `289c1e7aecf4c5bc2d342b846929c19c62e8ec12`

## 1. 目标

在现有独立 UAT 环境中，以接近真实业务的合成数据自动执行前端、后端和数据库联调，覆盖平台、物业、服务商六种角色。扫描需要发现页面渲染、接口调用、权限、字段映射和业务状态流转中的确定性缺陷；对确认的缺陷先补失败测试，再修复、回归并自动部署到 UAT。

本轮完成后应满足：

1. SA、SE、PL、PC、VL、CO 六种角色均有自动登录和可见菜单扫描。
2. 桌面端全部角色菜单以及移动端四个主要入口能够使用真实后端接口加载。
3. 核心业务至少覆盖“创建或选择种子数据 → 分配 → 处理 → 回款/结算 → 查询”的跨角色闭环。
4. 自动发现未捕获的浏览器异常、资源失败、意外 HTTP 4xx/5xx、权限越界、错误字段和前后状态不一致。
5. 每个失败都有角色、页面、步骤、请求、响应、截图或 trace 等可复现证据。
6. 只有稳定复现且期望明确的问题才自动修复；需求歧义只形成报告，不擅自修改业务规则。

## 2. 已选方案

采用“全角色业务旅程矩阵”，而不是只做页面爬行或只做接口模糊测试。

- 页面爬行负责广度：覆盖角色可见菜单、公共页、桌面和移动路由。
- 现有 Playwright 用户故事与新增跨角色旅程负责业务深度。
- OpenAPI、路由覆盖、后端测试和关键响应断言负责接口与数据契约。
- PostgreSQL 只作为 UAT 后端的持久层使用；测试通过公开 API 和页面验证状态，不在浏览器测试中直接改库。

## 3. 安全边界与非目标

- 只使用 `huicui-uat` Compose project、网络和 `huicui-uat-pgdata` 数据卷。
- 不读取、导入或修改生产数据库，不复制真实姓名、手机号、房号、录音、凭据或数据库 dump。
- 身份信息使用固定合成账号；新增业务数据使用带运行编号的合成名称和编号。
- 不发送真实短信，不调用真实支付、存证、ASR、LLM 或其他外部供应商。
- 不把符合产品规则的 401、403、404、409、422 或关闭通道状态误判为缺陷；测试必须为每个预期拒绝显式声明状态。
- 不为通过测试而放宽角色权限、删除校验或绕过审计。
- 不自动执行依赖的破坏性大版本升级。`npm audit` 发现的问题单独评估，不运行 `npm audit fix --force`。

## 4. 数据生命周期

### 4.1 固定角色

复用 `DevSeeder` 的六角色合成账号：

| 角色 | 账号 | 组织视角 |
| --- | --- | --- |
| SA | `admin` | 平台超管 |
| SE | `plat_se` | 平台员工 |
| PL | `cuihu_pl` | 翠湖物业负责人 |
| PC | `cuihu_pc` | 翠湖物业协调员 |
| VL | `jx_vl` | 捷信服务商负责人 |
| CO | `jx_co1` | 捷信催收员 |

UAT 口令继续由服务器 `/root/huicui-uat.env` 中的随机 `UAT_DEV_PASSWORD` 注入。口令不得写进 Git、日志、测试报告或聊天记录。

### 4.2 每轮重置

完整扫描开始前调用现有受保护流程：

```sh
UAT_ENV_FILE=/root/huicui-uat.env \
UAT_STATE_DIR=/var/lib/huicui-uat \
./deploy/uat/reset.sh --confirm huicui-uat
```

重置只允许删除并重建 `huicui-uat-pgdata`。脚本现有 fail-closed 校验必须保留；任何目标名称、状态目录或环境文件不符合约定时立即停止。普通代码部署和快速 smoke 不自动重置。

### 4.3 运行期业务数据

每轮生成唯一 `runId`，格式为 `E2E-YYYYMMDD-HHMMSS-<短随机串>`。需要新增的项目、批次、案件、跟进和结算备注都包含该编号，使失败证据可关联，重跑时不会误命中旧数据。

测试不得依赖数据库自增 ID。需要跨角色继续操作时，从创建接口响应或页面可见业务编号取得 ID，并通过 Playwright fixture 在同一串行旅程内传递。

## 5. 扫描架构

```text
受保护 UAT reset
       |
       v
固定 seed + 本轮 runId 数据
       |
       +--> 静态门禁：OpenAPI / 175 路由 / schema / build
       |
       +--> 六角色页面扫描：菜单 / 控制台 / 资源 / HTTP
       |
       +--> 跨角色业务闭环：创建 / 分配 / 处理 / 回款 / 结算
       |
       +--> 移动端扫描：主页 / 案件 / 通话 / 我的
       |
       v
统一 artifacts + 缺陷分类
       |
       +--> 明确缺陷：RED 测试 -> 单点修复 -> 回归
       |
       +--> 需求歧义：保留证据，等待产品确认
```

Playwright 保持单 worker 串行运行，避免共享 UAT 数据时发生竞态。每个角色使用独立 browser context，防止 token 和本地存储串号。

## 6. 覆盖矩阵

### 6.1 静态与后端基线

- `python3 backend/scripts/route_coverage.py`：OpenAPI 操作与 Controller handler 双向一致，目标为 175/175、无缺口。
- `npm run gen:api` 后检查 `frontend/src/api/schema.d.ts` 无漂移。
- `npm run build`：Vue 类型检查与生产构建通过。
- 后端 Maven 测试：所有单元/集成测试通过。
- `deploy/uat/tests/static-contract.sh`：自动部署、回滚、密钥和数据卷安全约束通过。
- 依赖扫描只产出分级报告；升级必须有独立验证，不能混入业务缺陷修复。

### 6.2 六角色页面扫描

页面扫描从 `frontend/src/constants/nav.ts` 的角色导航单一真源派生目标，不再维护第二份容易漂移的硬编码菜单表。对每个可见入口验证：

1. 点击后到达该角色允许的路由。
2. 页面出现明确的业务容器、空状态或无权限状态，不出现白屏。
3. 浏览器没有 `pageerror`、未处理 Promise 或严重 console error。
4. 当前页面发出的同源资源和 API 请求没有未声明的失败。
5. 角色菜单中不出现其无权访问的入口；直接访问越权路由会被路由守卫或后端拒绝。

页面扫描允许声明少量已知、符合设计的例外，例如不存在测试对象时的 404、业务校验 422、未授权探测 401。例外必须绑定具体方法和路径，禁止全局忽略所有 4xx。

### 6.3 核心跨角色闭环

完整旅程至少验证：

1. **组织与成员：** SA/SE 看到平台 SA/SE；PL 只管理本物业 PC；VL 只管理本服务商 CO；账号和完整手机号与接口一致。
2. **项目与批次：** 物业侧维护项目/批次信息，平台侧看到对应业务对象和负责人字段。
3. **派单与承接：** 平台选择服务商，VL 承接并分配 CO，角色视角中的状态保持一致。
4. **案件处理：** CO/PC 查询案件、添加跟进或承诺，管理角色能看到新状态和审计结果。
5. **回款与结算：** 合成回款进入对应批次，平台、物业和服务商按各自权限看到正确金额、状态和字段裁剪。
6. **查询与报表：** 全局搜索、工作台、经营报表和个人业绩能找到本轮或固定种子对象，数字与明细一致。

不可安全自动调用的真实外部动作只验证按钮门控、请求拦截或 dry-run 结果，不验证供应商成功回执。

### 6.4 移动端

使用移动视口覆盖 `/m`、`/m/cases`、案件详情、`/m/calls` 和 `/m/me`。验证导航、列表、详情和核心写操作不产生横向溢出、遮挡关键按钮或桌面路由误跳转。

## 7. 诊断与报告

新增统一 Playwright fixture，在每个测试中收集：

- `pageerror` 和分级 console 消息。
- 失败请求、HTTP 方法、脱敏 URL、状态码和截断后的脱敏响应摘要。
- 当前角色、账号、路由、测试步骤和 `runId`。
- 失败截图、trace、必要时的视频或 DOM 快照。

敏感请求头、token、密码、Cookie 和环境变量不得进入 artifact。手机号可在业务断言中使用固定合成值，但不能采集任何生产值。

结果按以下类别输出：

- `PRODUCT_BUG`：稳定复现且违反已确认规则。
- `TEST_BUG`：定位器、等待条件或测试数据假设错误。
- `EXPECTED_DENIAL`：符合权限或业务校验的拒绝。
- `ENVIRONMENT`：隧道、容器、浏览器或依赖环境问题。
- `REQUIREMENT_REVIEW`：现有规则不足以判断期望行为。

## 8. 自动修复流程

发现失败后严格执行：

1. 重跑最小场景，确认可以稳定复现。
2. 从页面请求、后端日志和数据状态定位故障边界及根因。
3. 对产品缺陷编写最小失败回归测试并观察预期失败。
4. 只修改根因所在的最小代码范围，不顺带重构无关模块。
5. 运行目标测试确认转绿，再运行相邻场景和完整回归。
6. 需求不明确或涉及业务规则变化时停止自动修复，保留报告等待确认。

测试本身的错误不通过修改生产代码掩盖。环境错误先修复测试基础设施，再继续业务扫描。

## 9. 执行与部署

提供单一入口脚本，顺序执行：

1. 校验目标是 `huicui-uat`，记录 active SHA 和数据卷信息。
2. 显式重置 UAT 并等待 db、backend、web 健康。
3. 执行 `verify.sh` 快速门禁。
4. 执行六角色页面扫描、核心业务闭环、移动端和现有全量 Playwright。
5. 执行静态、前端和后端回归。
6. 写入带时间戳和 SHA 的报告目录。

本地修复完成后先运行全部门禁，再提交到功能分支。集成到 `main` 并推送 `backup/main` 后，由现有 post-receive hook 自动部署；部署自身继续运行快速 smoke。自动部署失败时保留日志并回退上一健康镜像，不删除 UAT 数据卷。

## 10. 计划新增或修改的文件

- `frontend/e2e/fixtures/diagnostics.ts`：收集控制台、页面和网络失败并做敏感字段脱敏。
- `frontend/e2e/helpers.ts`：继续作为六角色账号单一真源，并补充本轮业务数据辅助函数；不再新建重复的角色表。
- `frontend/e2e/role-page-scan.spec.ts`：从导航单一真源派生的六角色页面扫描。
- `frontend/e2e/business-lifecycle.spec.ts`：串行跨角色业务闭环。
- `frontend/e2e/mobile-role-scan.spec.ts`：移动端主要入口和关键操作。
- `frontend/playwright.full-scan.config.ts`：全扫描 reporter、artifact 和超时配置；桌面项目运行完整套件，移动项目只匹配移动端扫描文件。
- `deploy/uat/Dockerfile.smoke`：在保持快速 smoke 默认入口的前提下包含全扫描所需测试与导航源。
- `deploy/uat/docker-compose.uat.yml`：增加显式启用的 full-scan profile 或命令，不改变日常 smoke。
- `deploy/uat/full-scan.sh`：受保护重置、测试编排、报告和状态输出。
- `deploy/uat/tests/full-scan-contract.sh`：验证 reset 目标、密钥不进 argv/日志、profile 和 artifact 安全约束。
- `deploy/uat/README.md`：补充全扫描、报告、失败分类和人工测试并存规则。

实际扫描若暴露产品缺陷，按根因修改对应前端、后端、OpenAPI 或种子文件，并为每个缺陷提交独立回归测试。

## 11. 验收标准

1. 六角色所有可见菜单均被自动访问，且没有未声明的 page error、严重 console error 或 HTTP 失败。
2. 越权菜单不可见，越权直达和 API 请求得到预期拦截，不发生跨组织数据泄漏。
3. 组织和成员账号、姓名、角色及完整合成手机号与 API 一致，并保持 BR-M1-04a 边界。
4. 核心跨角色业务闭环完成，关键状态和金额在前端、API 和后续角色视角中一致。
5. 桌面和移动端关键页面无白屏、主要控件不可达或严重布局阻断。
6. 每个失败均产生可定位且不泄密的 artifact；报告可以区分产品、测试、权限、环境和需求问题。
7. 每个自动修复都有可证明的 red-green 回归测试，相关测试和全量回归通过。
8. 修复后的 `main` 由现有 hook 自动部署到 UAT，active SHA 与内网 Git `main` 一致，原有非 UAT 服务保持健康。
